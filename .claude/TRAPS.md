# Traps we already hit

Read when you touch the area named in a bullet, or before debugging something odd. One owner doc for traps; add new ones here (date + what + the rule), not in STATUS.

- **A foreign loader in the game folder kills `nro` instances at launch (2026-11-06).** At 15:46 something put `winmm.dll` (the same loader as the Nucleus handler's) and a `dlllist.txt` naming `OnlineFix64.dll` (absent) into the real game folder; `nro` stages the loose files, and instance 1 exited with code 0 about 15 s after launch ("P-module failed: alive=false, 0 modules"). Moved to `Z:/nrpvp-backup/game-folder-2026-11-06/`, the next run was fine. On a launch that dies at once, list the game folder for files newer than the game's own before blaming the build.
- **"The game window is not in front" with no screensaver (2026-11-05):** the Windows search flyout (`SearchHost`) held the foreground and two `mi-duo-party` runs aborted at the title. Look at the foreground process before blaming the build; a person may be using the PC.
- **Commence is not one path (2026-11-05).** `exe+0x9EEBE0` runs only without a party; in a party the press goes to `exe+0x9ED090` (MEMORY_MAP §13), so a trace on the first shows nothing there. And `menu+0x1338` / `+0x10C4` told our card only on the save they were measured on: a Commence on the card on another save was a normal expedition ("Matchmaking failed"). Read the target list instead. Any test of the menu flow must set Number of Players itself: the ring byte in the save was Trio, which refuses the queue with no party (`queue_br` does).
- **An item in the list is chosen by F, not by the cursor (2026-11-05):** `Up` moves the highlight; the target list changes only on F, and the next F is Commence. `br_card` reads the list, so it says `no` while the highlight is already on our card.
- **`read_ptr` refuses the end of a `vector<i32>` (2026-11-05):** it asks for 8-byte alignment; read such a pair with `read_u64`.
- **Flag 10007420 stays in a test save (2026-11-03).** Our flag group is saved, so an older scenario's `flag 10007420 1` leaves the die-at-once effect 102130 on in later runs: `hp0` is then a death with no downed state (`M5-8 LOCAL ... speffects of interest: [102130]`, `flag 10007420: set ON (was ON)`). A scenario that needs a downed player sets `flag 10007420 0` first (`mi-killfeed`). Players' saves never set it, **but Leonardo's does**: the single-game scenarios run on his real Steam account, so in the friend session of 2026-11-07 he died at once with no downed state (FS7-6). The mod's reset at the expedition's end never ran (`world.night` is `None` outside an expedition).
- **Arena flags 10007520 / 10007519 stay in the save (2026-11-20).** Same cause as 10007420: Leonardo closed the game ~20 s after an Arena bot match ended (`dist\logs\nrpvp_2026-11-17_22-31-13.log`: `immortality on`, `match over, WIN 2-0`, no `immortality off`; the DLL clears it only once LOCAL leaves the arena). Three days later his Battle Royale bot match (player zip v0.3.2, `nrpvp_2026-11-20_14-28-00.log`) was immortal: bot hits dropped his HP (`T-033 hit` lines) but event 99100920 stopped them at 1 HP. The DLL never wrote the flag that session because it wrote OFF only after its own ON. Fixed: `arenarounds::saved_flag_write_due` writes the wanted value on the first tick of every session. Any new saved flag of ours that grants a state needs the same first-tick write.
- **An idle match ends by itself (2026-11-03).** The toast "If you continue to remain inactive you will be removed from session" came first; 12 minutes after the expedition started both instances left the session, the world was torn down and both crashed with 0xC0000374 (runs `1793716947` / `953`). Camera movement by `mousemove` did not stop it; which input counts, and whether the game or Seamless Co-op does this, is UNKNOWN. Keep a `teardown = "keep"` lab under 12 minutes, or end the lab and start again.
- **Pin beam photos (2026-11-03):** the ground after `hawk_drop` can be walled in by rocks and fog, where no beam shows even with the filter off: a PASS from there proves nothing. Take them during the hawk flight with the pin ahead (`mi-pin-beam`); the map does not open in about the first 10 s of the ride. A removed beam fades for some seconds, so a photo right after a pin moves can still show the old one.
- **Nucleus `dlllist.txt` must not end with a newline.** It makes Nucleus fail with "WaitForSingleObject failed 258". The deploy script writes it correctly; never edit it by hand.
- **Under Nucleus, keys reach a window only when it has focus** (END unlocks input). Use the console instead: `nrcon --all <cmd>` reaches every instance.
- **Nucleus deletes its instance folders on close.** Logs go to `dist\nucleus-logs\` for that reason.
- **Nucleus does not load our game-data package when it starts the game through Seamless Co-op's launcher** (the plain deploy):
  no no-boss nights, vanilla hawk route. `deploy-nucleus.ps1 -Me3` (start through our launcher / me3) was removed: window 2 stopped on ColdLoader "appid not found"
  (2026-10-23, cause UNKNOWN). Use the plain deploy. Event-script features are tested with `nro` (offline mode, puppets, `mi-*` instances; TOOLS.md); under Nucleus use the dev console
  (`flag`, `clock`) instead.
- **Never run the scanner or any tool against the normal game.** Steam launch = vanilla with anti-cheat. Mods only through Nucleus, `nrpvp_launcher.exe`, `scripts\launch.ps1` or `nro` (me3 profile with its preflight).

  `EncryptERNRRegulation`) encrypts a Nightreign regulation with the Elden Ring AES key: the game closes ~10 s after start, no crash
  dump (Witchy reads with the ER key first, so re-unpacking its own output looks fine). Our own Python writer (NR key, identical BND4,

- **Never touch the vanilla saves** (`%APPDATA%\Nightreign\<id>\NR0000.sl2*`).
- **Player ids change between the lobby and the expedition** (run 21: joiners were `0x6003`/`0x6004` in the lobby, `0x6002`/`0x6003` in
  the expedition). Teams are only meaningful once the expedition has loaded; do not decide or show teams from lobby ids.
- **Addresses change every launch and every area load.** A value found by the scanner is only good for that run; the mod must reach it through the player object (see `re/MEMORY_MAP.md`). A scanner left watching a fixed address after a restart is looking at the wrong memory: stop it.
- **Double-check offsets before any write.** On 2026-10-12 a test wrote to `+0x728/+0x72C` instead of `+0x718/+0x71C` by mistake (no lasting effect).
- **Setting health to 0 does not kill** in a multiplayer session; it downs. Death is the bleed-out clock reaching 0.
- **Elden Ring layouts are hints only.** Several were wrong in Nightreign (list in `re/MEMORY_MAP.md` §9).
- **No `VirtualQuery`-guarded reads on the main loop.** They made each pass take 2–3 s in an expedition (run 15). Use `mem::read` or
  `RegionCache::direct()` there (the guarded `RegionCache::new()` is test-only since R5). The heartbeat line shows the pass time.
- **Only a lobby the game makes can be joined.** Our own `CreateLobby(Public, 6)` gets adopted by Seamless Co-op but joiners' games
  leave it at once, and a direct `JoinLobby` gives Steam membership without the game session (FS-MM2). Steam lobby membership is not
  presence: ALL PRESENT also needs the host's ChrSet to hold the players.
- **`RegionCache::readable_len` is a `VirtualQuery` even on the direct cache.** `flags::locate` used it; 12 flag reads per tick made the
  main loop take 0.6 s (solo) to 2.4 s (Nucleus) per pass (2026-10-23). Read flags only through the fixed `locate` (plain copies).
- **Nucleus has the vanilla night**: minions, the wipe check (both down = game over for both) and the night freeze (a knocked player
  inside the circle never bleeds out). Never put both players on team 6 at night there (1182 counts them out → instant wipe); use
  console `god 1` on the knocking player instead. `clock end` on a fresh day kills everyone outside the closed circle: use
  `clock circle` and walk in.

- **Sonnet agents can be cut off by usage limits mid-task.** Check `cargo build` and `git status` before trusting the tree; the task card says what was intended.
- **Hardware breakpoints are a shared budget of four** (player build: `menuflow` holds slots 2 and 3 for the whole session and never clears them, so only slots 0 and 1 are free in an expedition; `reviveblock` takes up to 2 while someone is downed, the deathhold takes 1 for the hold and, at the release, 1 for gate A and after 2 s 1 more for gate B. It works only because downed, dead and releasing never overlap. `game/itemdrop.rs` (RW-3, host only) takes any free slot (`hwbp::is_free`) for about one frame per drop and logs a line if none is free. A claim/release API with owner ids is still an open idea (`hwbp.rs` has set / clear / is_free only); `hwbp::set` silently overwrites whoever holds a slot) (2026-10-24): hold, gate, reviveblock, menu/matchmaking and, in dev, the puppets (three) all draw on them (`hwbp.rs`). The M5-9 release failed with puppets present because the start breakpoint stayed armed while the gate wanted a slot (fixed). Any new feature that needs a breakpoint states how many slots it holds at peak and frees them when done.
- **Offline solo carries SpEffect 6999500** (a revive item on the script's list), so the die-at-once rule is OFF there; a death there needs `flag 10007420 1` (SpEffect 102130, die at once) first; the RW scenarios do that.

- **`rawcall` into the game's equip function crashed the game** (ARENA-3 spike, 2026-11-09): `rawcall 1F3430 <EquipGameData> 0 <index> 1`
  from our main loop killed the process at once, while the add-item call (`give`) was fine. The equip path rebuilds the character
  model (`exe+0x1F11A0`); call such functions only from the game's own thread (the RW-3 drop needed a breakpoint for the same reason,
  `game/itemdrop.rs`), and never in a run you cannot lose.
- **`arena_loadout apply` at the Roundtable froze the game** (ARENA-LV research, 2026-11-12, one emulated instance): the queued
  game-thread call armed its breakpoint (hwbp slot 0), then the main loop and the console pipe stopped for good (`All pipe
  instances are busy`); only `nro stop --all` ended it. The Arena only calls it on the arena spawn, where it works; keep the console
  `apply` for an expedition, or expect to lose the instance.
- **An item we equip shows only on our own screen** (Arena test 2026-11-12): the game's add / equip calls change LOCAL's inventory and
  model but never tell the session; every other game keeps drawing the old weapon. After any equipment change made by the mod, call
  the game's player-data broadcast `exe+0xDE20E0()` on the game thread (`inventory::send_player_data_on_game_thread`; MEMORY_MAP §29).
  Check with the console `rival_gear` on the other instance, not with your own screenshot.
- **Never get a player up by writing `PlayerIns+0x732`** (Arena tests 2026-11-12 and 2026-11-15, spike 2026-11-16): the byte makes the
  game's code lead and the revival animation must follow on the next frame. A write later than ~3.5 s after the down skips the get-up
  (state 1 -> 0, no state 2) and the player dies ~3 s later, with a level lost: 8 of 8 on one PC, and Samuel's lost round on real
  Steam. Spacing the retries (1 s, then 2.5 s) only moved the problem. Empty the revive bar instead (`+0x714` = 0, pause `+0x71C` up),
  as a teammate's revive does: MEMORY_MAP §6.
- **A lobby left over after a match turns the next card pick into a vanilla run** (MM-REQ, 2026-11-13): see MEMORY_MAP §25 "The game's
  lobby object"; `matchstart::request_leave_if_alone` leaves it when we are its only member.
- **A saved GitHub token breaks updates from the public releases repository** (2026-11-13): GitHub answers 401 to an expired or
  revoked token even when the repository is public, so a launcher that still sent the old "Private updates" token showed "No release
  found". The launcher sends no token at all and deletes the old token file on startup (RELEASE.md §6).
- **A squash merge of dev into main makes the next dev → main PR conflict** (2026-11-13): the squash commit shares no history with
  dev, so git sees every change twice. Fixed once with `git merge -s ours origin/main` on dev (main's tree equalled a dev commit);
  the repository now allows merge commits only (DECISIONS 2026-11-13).
- **A release version below the installed one never reaches that player** (2026-11-13): the launcher refuses downgrades, and the
  new releases repository restarted at 0.1.x below the 0.2.0 testers had. Raise the workspace version instead (RELEASE.md §6).
- **A text search-and-replace in Rust code breaks the release's format check** (2026-11-24): the Nightclash rename shortened
  strings, so rustfmt wanted two wrapped calls on one line; `cargo fmt --all --check` failed the first release build on `main`
  and no release was published. There is no CI on pull requests: after any bulk edit run the README's "Checks before a
  commit" (fmt, both clippy runs, tests) before the PR, and update `releases/notes.txt` before merging into `main`.
